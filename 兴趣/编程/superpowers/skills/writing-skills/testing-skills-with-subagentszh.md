# 使用子代理测试技能

**在以下情况下加载此参考：** 创建或编辑技能时、部署之前，以验证它们在压力下是否有效并能抵抗找借口规避的行为。

## 概述

**测试技能即是将 TDD 应用于流程文档。**
你在没有技能的情况下运行场景（红色 RED - 观察代理失败），编写解决这些失败的技能（绿色 GREEN - 观察代理服从），然后堵住漏洞（重构 REFACTOR - 保持合规）。

**核心原则：** 如果你没有看到代理在缺乏该技能的情况下失败，你就不知道该技能是否预防了正确的故障。

## TDD 在技能测试中的映射

| TDD 阶段 | 技能测试 | 你要做什么 |
|-----------|---------------|-------------|
| **RED** | 基准测试 (Baseline) | 在没有技能的情况下运行场景，观察代理失败 |
| **Verify RED** | 捕获借口 | 逐字记录确切的失败原因 |
| **GREEN** | 编写技能 | 解决观察到的具体基准故障 |
| **Verify GREEN** | 压力测试 | 在有技能的情况下运行场景，验证合规性 |
| **REFACTOR** | 堵住漏洞 | 寻找新的借口，添加反制措施 |

## RED 阶段：基准测试 (观察失败)

**流程：**
1. **创建压力场景**（结合 3 种以上压力）。
2. **在没有技能的情况下运行**。
3. **逐字记录选择和借口**。

## 压力类型

- **时间压力**：紧急情况、截止日期。
- **沉没成本**：已投入数小时工作，删掉太“浪费”。
- **权威压力**：上级要求跳过流程。
- **疲劳压力**：工作日结束，想回家。

## 堵住漏洞

如果代理违反了规则，你需要重构技能：
- **在规则中明确否定**：“禁止保留作为参考”，“删掉就是删掉”。
- **建立借口对照表**：列出借口与现实的对比。
- **创建危险信号清单**。

## 底线

**创建技能就是 TDD。相同的循环，相同的好处。**
如果你不写没有测试的代码，就不要写没有经过代理测试的技能。
