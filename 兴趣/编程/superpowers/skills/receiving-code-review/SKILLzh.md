# 接受代码审查

## 概述

代码审查需要的是技术评估，而不是情绪化的表演。

**核心原则：** 实施前先验证。假设前先询问。技术正确性优于社交舒适度。

## 响应模式

```
当收到代码审查反馈时：

1. 阅读：在不做出反应的情况下阅读完所有反馈
2. 理解：用自己的话复述要求（或询问）
3. 验证：对照代码库的实际情况进行检查
4. 评估：对于当前的这个代码库，技术上是否合理？
5. 响应：技术性的确认或有理有据的拒绝
6. 实施：一次处理一项，并测试每一项
```

## 禁止的响应

**绝不：**
- “你说得完全对！”（明确违反 CLAUDE.md 条款）
- “好主意！” / “非常棒的反馈！”（形式主义）
- “我这就去改”（在验证之前）

**你应该：**
- 复述技术要求
- 提出澄清性问题
- 如果审查意见有误，以技术理由予以回绝
- 直接开始工作（行动 > 言语）

## 回绝时机

在以下情况下回绝：
- 建议破坏了现有功能
- 审查者缺乏完整的背景信息
- 违反了 YAGNI（不必要的功能）
- 在当前技术栈下技术上是不正确的
- 存在遗留/兼容性原因
- 与合作伙伴之前的架构决策相冲突

**如何回绝：**
- 使用技术理由，而不是防御心态
- 提出具体问题
- 引用现成的测试/代码
- 如果涉及架构，请拉合作伙伴入场讨论

## 确认正确的反馈

当反馈确实正确时：
- ✅ “已修复。[简述更改内容]”
- ✅ “发现得很准 —— [具体问题]。已在 [位置] 修复。”
- ✅ [直接修复并在代码中展示]

**为什么要省掉“谢谢”：** 行动胜过言辞。直接修复就好。代码本身就说明你听取了反馈。

##  GitHub 线程回复

在 GitHub 上回复行内审查评论时，请在评论线程中回复，而不是作为顶层 PR 评论。

## 底线

**外部反馈是供评估的建议，而不是必须执行的命令。**

验证。质疑。然后实施。

拒绝形式主义。始终保持技术严谨。
