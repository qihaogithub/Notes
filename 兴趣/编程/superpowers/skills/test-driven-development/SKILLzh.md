# 测试驱动开发 (TDD)

## 概述

先写测试。观察它失败。编写最小代码使其通过。

**核心原则：** 如果你没有亲眼看到测试失败，你就不确定它是否测试了正确的东西。

**违反这些规则的字面要求即违反了规则的精神。**

## 铁律

```
在没有先行编写失败测试的情况下，禁止编写任何生产代码。
```

先写代码后写测试？删掉它。重新开始。

## 红-绿-重构 (Red-Green-Refactor)

1. **红 (RED) - 编写失败的测试**：编写一个展示预期行为的极简测试。
2. **验证红 - 观察失败**：**强制性，绝不跳过。** 确保测试因正确的原因失败。
3. **绿 (GREEN) - 最小化代码**：编写能使测试通过的最简单代码。
4. **验证绿 - 观察通过**：**强制性。** 确保所有测试都通过。
5. **重构 (REFACTOR) - 优化代码**：在保持测试通过的前提下清理代码。

## 为什么顺序很重要

**“我等之后再写测试来验证”**
在代码写好后再写的测试会立即通过。立即通过证明不了任何事情。
先写测试强制你看到测试失败，证明它确实在测试某些东西。

**“我之前已经花了几小时写代码，删掉太浪费了”**
沉没成本谬误。时间已经过去了。现在的选择是：
- 删掉并用 TDD 重写（高信心）。
- 保留并事后补测试（低信心，很可能残留 Bug）。
“浪费”是指保留了你无法信任的代码。

## 信号灯 —— 停止并重新开始

- 代码写在测试之前
- 测试在实施后才写
- 测试立即通过
- 无法解释测试为什么失败
- 借口“就这一次不按流程走”

**以上所有情况都意味着：删掉代码。用 TDD 重新开始。**
