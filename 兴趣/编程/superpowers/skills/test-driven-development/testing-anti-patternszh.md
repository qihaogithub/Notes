# 测试反模式 (Testing Anti-Patterns)

**在以下情况下加载参考：** 编写或更改测试、添加 Mock 或想要向生产代码添加仅供测试的方法时。

## 概述

测试必须验证真实的业务行为，而不是 Mock 的行为。Mock 只是隔离的手段，不是被测试的对象。

**核心原则：** 测试代码做了什么，而不是 Mock 做了什么。

**严格遵循 TDD 可以防止这些反模式。**

## 铁律

```
1. 严禁测试 Mock 的行为
2. 严禁向生产类添加仅供测试的方法
3. 严禁在不了解依赖项的情况下进行 Mock
```

## 反模式 1：测试 Mock 的行为

**错误示范：**
```typescript
// ❌ 错误：测试 Mock 元素是否存在
test('渲染侧边栏', () => {
  render(<Page />);
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
});
```

**原因：**
- 你在验证 Mock 是否工作，而不是组件是否工作。
- 这不能告诉你任何关于真实行为的信息。

**修复方案：**
- ✅ 正确：测试真实的组件行为，或者干脆不要 Mock 它。

---

## 反模式 2：生产品代码中的“仅供测试”方法

**错误示范：**
```typescript
class Session {
  async destroy() {  // 这个方法只在测试中用到
    await this._workspaceManager?.destroyWorkspace(this.id);
  }
}
```

**原因：**
- 生产类被仅供测试的代码污染。
- 违反了 YAGNI 和职责分离原则。

**修复方案：**
- ✅ 正确：将这些清理逻辑放入测试工具类中。

---

## 反模式 3：在不了解的情况下 Mock

**错误示范：**
过度的 Mock 导致测试通过的原因是错误的，或者完全破坏了测试逻辑依赖的副作用。

**门禁函数：**
在 Mock 任何方法之前：
1. 问：“真实方法有什么副作用？”
2. 问：“这个测试依赖这些副作用吗？”
3. 问：“我是否完全理解此测试的需求？”

---

## 反模式 4：不完整的 Mock

**错误示范：** 只 Mock 了你认为需要的几个字段。

**铁律：** Mock 现实中存在的完整数据结构，而不仅仅是你当前测试用到的那几个字段。

---

## 危险信号

- 断言检查 `*-mock`。
- 方法仅在测试文件中被调用。
- Mock 的设置代码占测试代码的 50% 以上。

## 底线

**Mock 是隔离工具，不是测试对象。**
如果你发现自己在测试 Mock 的行为，说明你偏离了 TDD。
