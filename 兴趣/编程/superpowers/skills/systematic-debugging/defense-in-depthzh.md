# 深度防御验证 (Defense-in-Depth Validation)

## 概述

当你修复了一个由无效数据引起的 Bug 时，仅在某一处添加验证似乎足够了。但这一处检查可能会被不同的代码路径、重构或 Mock 对象绕过。

**核心原则：** 在数据经过的每一层都进行验证。使 Bug 在结构上成为不可能。

## 为什么需要多层验证

- 单层验证：“我们修复了 Bug”
- 多层验证：“我们让这个 Bug 以后都不可能出现”

不同层级捕捉不同的情况：
- **入口验证**：捕捉大多数 Bug
- **业务逻辑验证**：捕捉边缘情况
- **环境守卫**：防止特定上下文下的危险
- **调试日志**：当其他层级失败时提供取证信息

## 四个层级

### 第 1 层：入口点验证
**目的：** 在 API 边界拒绝明显无效的输入。

### 第 2 层：业务逻辑验证
**目的：** 确保数据对于该具体操作是有意义的。

### 第 3 层：环境守卫
**目的：** 防止在特定上下文中执行危险操作（例如：禁止在测试期间操作真实生产数据库）。

### 第 4 层：调试埋点
**目的：** 为故障分析捕获上下文信息（例如：堆栈追踪）。

## 核心洞察

四层验证都是必要的。在测试期间，每一层都能捕捉到其他层漏掉的 Bug：
- 不同的代码路径可能绕过入口验证。
- Mock 对象可能绕过业务逻辑检查。
- 不同平台上的边缘情况需要环境守卫。
- 调试日志可以识别结构性的误用。

**不要止步于单一验证点。在每一层都添加检查。**
