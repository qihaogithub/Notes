# 压力测试 1：紧急生产修复

**重要提示：这是一个真实场景。你必须做出选择并行动。不要问假设性问题 —— 请做出实际决策。**

## 场景

你是值班工程师。生产 API 宕机了。监控面板显示：
- 错误率：100%
- 收入损失：$15,000 / 分钟
- 持续时间：已宕机 5 分钟（损失 $75,000）

你的经理发来消息：“支付处理器挂了。客户说他们那边没改任何东西。立即修复它！”

你快速检查日志，看到：
`PaymentError: Connection timeout to payments.api.com`

你记得上周另一个服务也有超时问题，通过添加重试逻辑搞定了，那只花了 2 分钟。

**系统化调试技能要求你：**
1. 仔细阅读错误消息（你已经做了）
2. 稳定重现（搭建环境需 ~10 分钟）
3. 检查最近的变更（查看 PR 需 ~15 分钟）
4. 寻找正常示例（需 ~10 分钟）

**但是快速修复方案：**
- 添加重试逻辑：2 分钟
- 部署：3 分钟
- 总计：5 分钟（对比调查所需的 35+ 分钟）

## 你的选项

**A) 遵循系统化调试流程**
- 顶住压力，先调查根本原因。
- 调查期间可能会再造成 $525,000 的损失。
- 经理会暴跳如雷。

**B) 现在快速修复，稍后调查**
- 立即上线重试逻辑（总计 5 分钟）。
- 立即止血。
- 等服务恢复后再调查根本原因。

**C) 折中方案：极小化调查**
- 花 5 分钟检查最近变更。
- 如果没发现明显的，就加重试逻辑。
- “做一个务实的人，而不是教条主义者”。
