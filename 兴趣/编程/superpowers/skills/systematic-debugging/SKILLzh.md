# 系统化调试

## 概述

随意的修复会浪费时间并创造新的 Bug。快速补丁往往会掩盖底层问题。

**核心原则：** 在尝试修复之前，务必（ALWAYS）找到根本原因。修复症状等同于失败。

**违反此流程的字面要求即违反了调试的精神。**

## 铁律

```
在进行根本原因调查之前，严禁直接尝试修复。
```

如果你还没有完成第 1 阶段，你不能提出任何修复建议。

## 四个阶段

你必须完成每一个阶段才能进入下一个阶段。

### 第 1 阶段：根本原因调查

1. **仔细阅读错误消息**：不要跳过错误或警告。
2. **稳定重现**：你能可靠地触发它吗？
3. **检查最近的变化**：什么改动可能导致此问题？
4. **追踪数据流**：坏值是从哪里来的？

### 第 2 阶段：模式分析

1. **寻找正常工作的示例**：在代码库中寻找类似的、正常工作的代码。
2. **对照参考资料**。
3. **识别差异**：正常与故障之间有什么区别？

### 第 3 阶段：假设与测试

1. **形成单一假设**：明确陈述：“我认为根本原因是 X，因为 Y。”
2. **进行极小化测试**：进行最小的更改来验证假设。
3. **继续前先验证**。

### 第 4 阶段：实施

1. **创建失败的测试用例**：在修复之前必须拥有它。
2. **实施单一修复**：一次只做一个改动。
3. **验证修复**。

## 信号灯 —— 停止执行并遵循流程

如果你发现自己在想：
- “先快速修一下，以后再查”
- “直接试着改改 X 看看行不行”
- “大概是 X 的问题，我修一下”

**以上所有想法都意味着：停止 (STOP)。回到第 1 阶段。**

## 铁一般的合理化预防

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单的问题也有根本原因。流程对简单 Bug 同样高效。 |
| “情况紧急，没时间走流程” | 系统化调试比“猜并测试”瞎折腾要快得多。 |
| “先试这个，然后再查” | 第一个修复就奠定了模式。应从一开始就做对。 |
| “我修完了再写测试” | 未经测试的修复站不住脚。先写测试才能证明一切。 |
