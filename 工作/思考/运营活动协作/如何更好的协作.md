## 📋 背景与协作困境

我是一名 UI 设计师，在日常工作中需要频繁与**运营设计师**进行协作。在共同推进各类活动项目时，我们遇到了诸多协作流程上的挑战。

> **修订说明**：开篇表明了个人视角，但作为团队协作指南，建议补充说明文档的共创目标。

## 🎯 活动项目的三种典型类型（与协作挑战）

根据开发模式与设计自由度，我们通常将活动项目分为以下三类，**每类都伴随着特定的协作挑战与机会点**：

### 1. 全新开发型活动
- **发起方**：活动运营
- **设计执行**：运营设计师
- **特点**：从零开始开发，设计自由度**极高**，通常由运营设计师主导视觉创意。
- **协作挑战**：易因前期缺乏**技术可行性**同步，导致中后期实现成本过高或方案反复。**需要早期、轻量的技术评审介入。**

### 2. 资源配置型活动
- **基础**：基于已上线项目的功能框架。
- **设计任务**：运营设计师需在既定功能范围内进行视觉设计，并按照**资源规范**进行切图与配置。
- **协作痛点**：对于逻辑复杂的活动，运营设计师理解配置规则与限制需要**耗费大量时间**。同时，交付的切图与标注资源质量直接影响开发效率。

### 3. 功能微调型活动
- **基础**：已上线项目，主体功能不变。
- **变更内容**：主要替换资源配置，并**新增或修改个别功能**。
- **协作挑战**：需要在既有约束下平衡视觉创新与功能可行性，对**变更影响的评估**与**沟通精度**要求很高。

> **不同类型活动的协作侧重**：
> - **资源配置型**：最易暴露“规范依赖”与“技能错位”问题，是流程优化的**关键切入点**。
> - **功能微调型**：更考验“角色职责”的清晰度与**变更管理**能力。
> - **全新开发型**：最需要**早期跨职能对齐**，避免创意与技术脱节。

## 🔍 核心协作问题（多视角分析）

当前的主要矛盾集中在**设计落地环节**，具体表现为以下三个层面。我们尝试从不同角色的视角理解这些问题：

### 1. 设计视角与技能错位
- **视角差异**：
- *运营设计师*：更关注**视觉表现力、创意冲击力与营销目标**。
- *UI 设计师/开发工程师*：必须同时考虑**技术实现成本、系统稳定性、性能与可维护性**。
- **技能错位与影响**：
- 运营设计师的核心技能在视觉创意，普遍**不熟悉前端切图、标注的工程化要求**。
- 其直接结果是：交付的设计资源（切图、标注）对开发工程师**不友好**，导致沟通成本激增、实现效果打折，甚至需要返工。
- **中立化表述**：这不是单方面的“技能不足”，而是**专业分工不同导致的交付物标准不一致**。问题在于缺乏一个清晰的、双方认可的“交接标准”。
**🛠️ 历史案例：长达五年的“切图之争”**
五年前，UI小U，开发小红，运营设计小花，小U收到开发小红的投诉，说小花的切图质量非常差，把他们整个开发组的逼疯了，希望ui能帮忙切图。小U非常震惊，因为小花是UI转岗到运营设计的，但是考虑到开发效率，小U直接问运营设计要了源文件，自己切图给开发，自此以后，运营设计与 UI 到底该谁来切图的争执持续至今。
### 2. 对“规范”的过度依赖与误解
**各方心态**：
- *运营设计方*：常期望获得一份**详尽、万能、能预判所有问题的规范**，以此规避协作风险和个人责任。
- *UI/系统搭建方*：疲于维护和解释一份试图覆盖所有“可能性”的复杂文档，认为这挤占了解决核心问题的时间。

**我们的共识**：
- **规范的本质是工具，不是保险**：规范的目的是高效处理**高频率、可复用的共性场景**，为协作建立基准。它无法、也不应该穷尽所有创新或特例。
- **动态沟通优于静态文档**：在快速迭代的业务中，**遇到问题并基于规范快速沟通、共同解决，是最高效的工作方式**。试图用一份静态文档替代沟通，会导致思维僵化和问题堆积。
- **规范需要共同维护**：规范应在解决典型问题的过程中迭代优化，而不是由单一角色闭门编写。

### 3. 角色职责与产出物归属的混淆
在协作中，对于“原型图”、“规范”、“项目文档”等产出物应由谁负责，存在普遍的混淆，模糊了**系统搭建者**与**系统使用者**的职责边界。

- **系统搭建者 (UI/开发)**：负责构建**可复用的活动系统与能力**，产出**系统层面的资源规范、组件库、技术方案**。核心职责是**提供能力并解答系统能力边界问题**。
- **系统使用者 (运营/运营设计)**：负责在具体业务项目中**使用系统能力达成业务目标**，产出**业务层面的原型图/草图、视觉稿、营销文案**。核心职责是**定义业务需求并确保设计在系统内可行**。

**效率陷阱分析**：
要求 UI 设计师为每一次活动都提供详细原型图，等同于要求“汽车工程师为每次出行设计临时图纸”。这混淆了角色：
1.  **低效**：让最懂系统但不一定最懂本次业务细节的人，去绘制业务沟通图，信息传递可能失真。
2.  **资源错配**：占用了 UI 设计师优化系统、处理复杂技术问题的核心时间，属于“高炮打蚊子”。
3.  **责任模糊**：当原型图由 UI 输出，业务方容易放弃对方案可行性的前期思考，将责任后置。

**核心原则**：**谁最了解当前业务的具体目标和细节，谁就主导该阶段核心沟通工具（如业务原型草图）的输出。** 其他角色提供专业支持与可行性审核。

## 🚀 提效的本质与可验证的原则

协作方式优化的最终目标是实现**团队整体效率提升**（即总工作量减少或价值产出增加）。为了更清晰地界定何为真正的提效，并使其可衡量，我们定义以下模型：

| 情况 | 描述 | 本质判断 | **可验证的迹象** |
| :--- | :--- | :--- | :--- |
| **✅ 情况一：双赢提效** | 通过流程优化，使协作双方工作量都减少。 | **真正提效**：团队总工作量减少。 | 项目周期缩短；双方对会议/沟通量的主观评价下降；返工率降低。 |
| **⚠️ 情况二：工作转移** | 通过流程改变，使一方工作量减少，但另一方增加。 | **甩锅而非提效**：总量不变，价值未增。 | 抱怨从 A 角色转移到 B 角色；问题解决环节后移；整体周期未变。 |
| **✅ 情况三：专业分工提效** | 引入更专业的资源/方式，以更小的总成本完成工作。 | **真正提效**：利用了比较优势。 | 专业资源（如 UI）处理复杂问题的时间增加；通用问题由模板/规范解决的速度加快。 |
| **❌ 情况四：创造冗余** | 引入新流程或资源，但团队总工作量反而增加。 | **效率降低**：过程复杂化。 | 文档变多但问题照旧；评审节点增加但决策质量未升；团队感到更“累”而非更“顺”。 |

### 对当前协作困境的启示与行动导向
1.  **摒弃“工作转移”**：要求 UI 为每次活动画原型图，或将所有问题解答写入规范，本质是 **“情况二”**。**我们的行动**：明确业务原型由业务方/运营设计输出，UI 提供反馈。
2.  **拥抱“专业分工提效”**：这正是 **“情况三”**。**我们的行动**：运营设计聚焦创意与业务表达，UI 聚焦系统与规范，开发聚焦实现。通过清晰的**交接标准**（如切图规范 Checklist）衔接。
3.  **警惕“创造冗余”**：过度文档化、为极小概率事件制定复杂流程，会导致 **“情况四”**。**我们的行动**：保持规范轻量、聚焦高频问题，鼓励针对特例的快速沟通。
4.  **设定验证指标**：在试行新流程后，通过**简单的复盘**，用上表“可验证的迹象”来评估我们处于哪种情况，并持续调整。

## 💡 高效协作的共识与具体行动

基于以上分析，我们共同向以下高效协作模式迈进：

### 1. 共识层面
- **规范观**：规范是**协作的基准线和加速器**，不是**规避沟通的免责声明**。
- **协作观**：**基于规范的主动沟通**比**等待完美的文档**更重要。
- **角色观**：清晰区分**系统搭建者**（提供“怎么做”的能力）与**系统使用者**（定义“做什么”的目标），并在项目中明确责任。

### 2. 具体行动项（近期可落地）
| 行动项                                | 负责人（倡议）              | 目标                                      | 产出物/衡量                                                   |
| :--------------------------------- | :------------------- | :-------------------------------------- | :------------------------------------------------------- |
| **A 1. 制定《开发友好型设计资源交付 Checklist》** | UI 设计师牵头，开发、运营设计评审   | 统一切图、标注、命名的交付标准，减少因资源问题导致的沟通。           | 一份一页纸的 Checklist（图片/示例）。**衡量**：开发接收资源后提出疑问的次数下降。         |
| **A 2. 明确“业务原型草图”输出方**             | 项目启动时明确（默认：运营设计师/运营） | 确保业务沟通由最懂需求的人主导，提升信息传递效率。               | 在项目 kickoff 会议纪要中明确。**衡量**：UI/开发在评审时问“这个为什么要这样？”的基础问题减少。 |
| **A 3. 建立“轻量技术预审”环节（针对全新开发型）**     | 运营设计师在概念阶段发起         | 在创意深化前，对齐技术可行性与大体成本，避免方向性返工。            | 一次 30 分钟的非正式技术碰头会。**衡量**：项目中后期因“实现不了”导致的重大方案变更减少。        |
| **A 4. 运营设计切图标注微培训**               | UI/开发提供支持            | 提升运营设计师交付物的工程友好度，赋能其技能树。                | 一次 15-30 分钟的分享会或图文指南。**衡量**：交付物首次通过 A 1 Checklist 的比例。   |
| **A 5. 季度协作案例复盘会**                 | 三方轮流发起               | 复盘 1-2 个典型项目，用“四种情况”模型诊断协作效率，同步信息，优化流程。 | 30-45 分钟的会议，产出几条待改进/待固化项。                                |

### 3. 长期共建方向
- **活动组件库/模板积累**：将已验证的、优秀的活动模式沉淀为可复用的组件或模板，进一步降低重复劳动的强度。
- **协作流程工具化**：探索使用协作工具（如 Figma 团队库、设计移交插件、项目管理模板）固化最佳实践。
